## 2. Provenance: which opencode version the local spec corresponds to

### 2a. Recorded Stainless spec (.stats.yml): provenance check, legacy generation

All audit comparisons use spec/openapi-opencode.json (the baseline in section 1). This subsection is a side check: .stats.yml claims to record the tracking spec, so the task verified what that record contains. Downloaded the URL recorded in .stats.yml (https://storage.googleapis.com/stainless-sdk-openapi-specs/opencode%2Fopencode-62d8fccba4eb8dc3a80434e0849eab3352e49fb96a718bb7b6d17ed8e582b716.yml): 86,466 bytes, md5 4ff9376cf9634e91731e63fe482ea532, exactly the recorded openapi_spec_hash. The bucket serves the same generation the SDK was last generated against; no newer generation exists at that URL.

That spec is a legacy generation: OpenAPI 3.0.0, 23 paths, 26 operations, 60 schemas, camelCase operationIds (getEvent, postSessionByIdMessage), and a pre-1.x sst-era surface (GET /app, POST /app/init, GET /mode, GET /log). The SDK's own resources (20+ modules, auth.set, session.prompt, vcs.diff) do not match it. Conclusion: the recorded Stainless generation is a historical artifact; the fork's actual tracking surface is the local spec.

### 2b. 1.18 source used for this audit (high confidence)

Source: anomalyco/opencode repo, packages/sdk/openapi.json at tag v1.18.11 (commit a1ab489e, 2026-07-30; repo default branch dev). Raw URL: https://raw.githubusercontent.com/anomalyco/opencode/v1.18.11/packages/sdk/openapi.json. Downloaded: 1,060,866 bytes, sha256 5bbd6493a1a488ef4294889341c896e420f814ecea95822100aaa9f3f95ab2d1.

The repo file is generated from the server's HttpApi route declarations (packages/opencode/src/server/routes/instance/httpapi/public.ts; see packages/opencode/specs/openapi-translation-cleanup.md), so the tag-pinned file is the authoritative API surface for that release.

Local spec equals the v1.18.11 spec. Canonical JSON comparison (recursively key-sorted, whitespace-insensitive): the two documents are identical except the repo file carries x-codeSamples (JS SDK usage samples) on operations, which the local copy lacks. After stripping x-codeSamples the documents are canonically equal: same 162 paths, same 188 operationIds, same parameter sets (name/in/required), same 472 schema names and property sets. The local spec also carries the v1.18.11-only interleaved widening (section 3), which dates it to v1.18.11 or newer (2026-07-30). Formatting differs (local: 4-space indent, no samples).

Secondary sources checked: the opencode.ai changelog (https://opencode.ai/changelog) for the 1.18.x entries; the changelog's API-relevant entries match the spec deltas found (section 3). The docs-site spec (packages/docs/openapi.json in the repo) is a stub; opencode.ai/docs derives from the same generated spec. The Stainless bucket serves no newer generation (2a).

## 4. SDK impact mapping

### 4a. 1.18 deltas (only two)

1. Config.subagent_depth goes into src/opencode_ai/types/config.py (class Config) and src/opencode_ai/types/config_update_params.py, plus api.md. Confirmed absent: grep for subagent_depth in src/opencode_ai has zero hits. Hand-add as int with minimum 0. This is the only 1.18 compat gap in the implemented surface.
2. interleaved widening: ProviderConfig.models.<id>.interleaved (types/config.py:256) and Model.capabilities.interleaved (types/model.py) are already modeled as Union[Literal[True], object], which is permissive; the widening is absorbed with no change. Optional tightening (section 5).

Each op needs sync and async methods and schema-driven param/response types under src/opencode_ai/types/ (new files for the v2, global, tool, worktree, experimental families; api.md regeneration or hand-edits).

### 4c. Collision with the fork's custom addressing work

The fork adds directory and workspace query params to every v1 method it implements (verified across all modules; auth.set and auth.remove are the only v1 methods without them, in src/opencode_ai/resources/auth.py). The upstream spec advertises directory plus workspace query params on exactly 119 of 188 operations: all v1 instance routes including the experimental/tool and experimental/worktree routes; the 69 without are auth (2), global (6), experimental.controlPlane.moveSession, and the v2 surface except v2.session.list. The fork and the spec agree on where addressing applies. The 1.18 line touches none of this, so no collision from the release.

v2.session.list is the only v2 operation with directory and workspace, and it adds project, subpath, cursor query params the fork's AddressingParams type does not cover. If v2 resources are added, extend AddressingParams (or add a v2 variant); the body-versus-query directory collision already has a precedent in sync.replay (query_directory rename, src/opencode_ai/resources/sync.py).

Watch item: upstream is trimming spec-only params (packages/opencode/specs/openapi-translation-cleanup.md at v1.18.11: InstanceQueryParameters previously injected directory and workspace "even when the runtime query schema did not accept them", advertising calls "that could fail with 400 at runtime"). The cleanup is in progress (drift tests merged); the v1.18.11 spec still advertises the params, but a future release may drop them from some routes. The fork's addressing work depends on those params being accepted.

## 5. Recommendation

### Must

1. Add subagent_depth to Config and the config-update params (src/opencode_ai/types/config.py, src/opencode_ai/types/config_update_params.py, api.md). Hand-edit; do not regenerate. This is the only 1.18 compat change in the implemented surface. int, minimum 0, optional.
2. Pin the spec's provenance. spec/openapi-opencode.json is already the v1.18.11 surface; record its source (anomalyco/opencode packages/sdk/openapi.json at tag v1.18.11) next to the file or in the README, and re-pull per release instead of ad-hoc copies.
3. Reconcile .stats.yml. The recorded URL and hash (verified, md5 matches) is a legacy Stainless generation (26 ops) that no longer describes the server API. Keep it as the historical generation record, but stop treating it as the tracking spec. If the fork ever regenerates via Stainless, the project must be re-provisioned; the current URL will not produce the 188-op surface.

### Should

4. Add the 28 non-v2 missing operations (global 6, experimental 16, tool 2, worktree 4) as new resource modules. Small, stable surface, same addressing pattern as existing v1 methods, no new addressing vocabulary.
5. Decide on the v2 API (61 operations) explicitly. It is where opencode is investing (9 to 24 to 61 ops across 1.15 to 1.17, stable in 1.18; it is the "current-server" API the desktop app uses). If fork users target it, hand-write resources/v2/* from the spec; do not regenerate via Stainless, the input is stale. If not, document the gap in the README.

### Optional

6. Tighten interleaved to the widened union (Literal[reasoning, reasoning_content, reasoning_text] | str | Literal[True] | object) now that the spec enumerates the string variants.
7. Track the upstream openapi-translation-cleanup; test the fork's directory and workspace params against a real 1.18 server if the cleanup lands, since it may de-advertise (and possibly reject) them on some routes.
8. Once v2 resources exist, write a v1-to-v2 migration note (v2 uses project, subpath, cursor addressing).

### Breaking changes for users

None in the 1.18 line for the implemented surface: no renamed or removed operations or parameters, no changed types (the interleaved widening is additive and already tolerated by the loose Union[Literal[True], object] modeling; subagent_depth is additive). The 89 missing operations are coverage gaps, not breakage.

## Summary

1.18 changed almost nothing API-wise: Config.subagent_depth (add it to types/config.py and config_update_params.py) and an interleaved enum widening that the SDK already tolerates. The local spec is already at the v1.18.11 surface, and .stats.yml's recorded spec is a legacy 26-op generation to stop treating as the tracking source. The real gap is coverage: 89 spec operations unimplemented (global, experimental, tool, worktree, plus the 61-op v2 API). Decide whether v2 is in scope, then hand-edit: regeneration via Stainless is not viable with the stale recorded input.
